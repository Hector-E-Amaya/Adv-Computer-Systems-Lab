# Analysis: SIMD advantage on an Intel Core i3-1125G4 (Tiger Lake)

All numbers come from `data/processed/` and `reports/RESULTS_TABLES.md`
(generated by `scripts/analyze.py`). Each point is the median of 3 full
repetitions, and each repetition is the median of 7 timed trials. Speedup is
scalar time / SIMD time, computed within each repetition. Machine, builds and
hypotheses are in `reports/HYPOTHESES.md`, which was committed before any
measurement.

## Summary of hypotheses

| | Prediction | Result | Verdict |
|---|---|---|---|
| H1 | avx2 4-8x, sse2 2-4x vs scalar in L1 (saxpy f32) | avx2 **6.0x**, sse2 **3.0x** | holds |
| H2 | speedup falls to 1.1-1.6x in DRAM | **1.05x** (saxpy, mul f32) | direction holds; collapse is more complete than predicted |
| H3 | drops near N = 6K (L1), 160K (L2), ~1M (L3) | between 6144 and 8192; between 131K and 196K; gradual 786K-1.5M | holds |
| H4 | fp64 = half the fp32 element rate | **0.50x** in L1, **0.47x** in DRAM (saxpy avx2) | holds |
| H5 | misalignment 10-30% in L1/L2; tails only for N < ~100 | tails hold; misalignment up to **1.93x** (avx512, L1) | tails hold; alignment cost much larger than predicted |
| H6 | stride kills the SIMD gain; bandwidth flattens past one line | speedup ~1.0x for every stride >= 2; bandwidth keeps falling past stride 16 | first half holds; flattening not observed |
| H7 | avx512 at most 1.2x over avx2 in L1, none in DRAM | **1.79x** in L1, 1.00x in DRAM | **falsified** in L1, holds in DRAM |
| H8 | plain dot does not vectorize, about 1x; omp simd dot memory-bound in DRAM | plain dot is *partly* vectorized but still 0.97-1.08x; omp simd dot **2.9x** even in DRAM | performance claim holds; mechanism and DRAM claim wrong |
| H9 | all kernels memory-bound in DRAM | every SIMD kernel sits at the DRAM roof (once write-allocate is counted) | holds |

## 1. Vectorization is verified, not assumed

`reports/VECTORIZATION.md` checks, per build and per function, the gcc
`-fopt-info-vec` report against the generated assembly (`build/asm/`):

- **scalar:** zero vectorized loops and zero packed FP instructions. This
  required leaving `-fopenmp-simd` out of the scalar build: GCC vectorizes
  `#pragma omp simd` loops even under `-fno-tree-vectorize`.
- **sse2 / avx2 / avx512:** every unit-stride kernel uses the full register
  width of its build (xmm 16 B, ymm 32 B, zmm 64 B). avx2/avx512 use FMA
  (`vfmadd*ps`), since `-ffp-contract=fast` is set explicitly.
- **Strided saxpy** is reported "vectorized", but only for a special case.
  GCC *versions the loop on the stride*: every build begins with
  `cmpq $1, %rdx; jne`. The vector loop runs only when stride == 1 at run
  time. Any other stride takes a plain scalar loop (`vmovss` /
  `vfmadd213ss` / `vmovss` in avx2). There are no gather/scatter
  instructions in any build. So "loop vectorized" in the compiler report
  says nothing about the stride > 1 path that actually runs. This matters
  in Section 5.
- **Plain dot** is compiled as an *in-order* reduction (Section 7).

## 2. Locality: where the SIMD gain lives (H1, H2, H3, H7)

Figures: `plots/size_speedup_f32.png`, `plots/size_gflops_f32.png` (and
`_f64`).

saxpy f32 GFLOP/s at selected sizes:

| regime | scalar | sse2 | avx2 | avx512 |
|---|---|---|---|---|
| L1 | 5.30 | 15.90 | 31.52 | 56.98 |
| L2 | 5.24 | 12.57 | 18.73 | 25.47 |
| L3 | 5.34 | 11.34 | 11.91 | 11.38 |
| DRAM | 3.26 | 3.38 | 3.42 | 3.37 |

**In L1 the speedup follows the lane count.** In cycles per *vector loop
iteration* at N=1024, saxpy f32 costs 2.06 (sse2, 4 lanes), 1.94 (avx2, 8)
and 2.04 (avx512, 16). The iteration cost is constant at about 2 cycles
whatever the width. That is consistent with a per-iteration limit in the
load/store pipeline: 2 loads + 1 store per iteration, with the FMA unit only
about a quarter busy. Each doubling of width therefore doubles throughput:
sse2 3.0x, avx2 6.0x, avx512 10.75x. This is also why **H7 fails**. The
measured FMA peak of avx512 equals avx2 (Section 6: one 512-bit FMA unit on
this client core), but saxpy in L1 is not FMA-bound. It is bound by the
iteration rate, and a zmm iteration moves twice the bytes of a ymm one.

**Transitions match the cache sizes (H3).** With 2 arrays of 4 bytes, the
predicted boundaries are N = 6144 (48 KB L1), 160K (1.25 MB L2) and ~1M
(8 MB L3). Measured avx512 saxpy:
- 52.9 GFLOP/s at N=6144, then 30.8 at N=8192;
- 25.5 at N=131072, then 12.7 at N=196608;
- a gradual L3 to DRAM decline from N=786K (10.6) to N=1.5M (5.3).

The L3 edge is soft, as predicted: L3 is shared, and its 8 MB includes other
cores' and the OS's data.

**Outside L1 the gain shrinks, then vanishes (H2).**
- **L2:** avx512 only 4.95x (saxpy f32).
- **L3:** sse2, avx2 and avx512 all reach the same ~11.3-11.9 GFLOP/s.
  Every SIMD build hits the L3 bandwidth limit, so width no longer matters.
- **DRAM:** all four builds, *including scalar*, deliver 3.3-3.4 GFLOP/s,
  i.e. about 20.5 GB/s of useful traffic, at the measured DRAM read
  bandwidth of 21 GB/s. The prediction of 1.1-1.6x was too optimistic:
  scalar code already saturates single-core DRAM bandwidth for saxpy, so
  1.05x is all that is left.

The stencil keeps a modest 1.26-1.30x in DRAM. Its scalar version is
compute-bound (Section 6), not memory-bound.

## 3. fp32 vs fp64 (H4)

Figure: `plots/dtype_ratio.png`. fp64 has half the lanes per register, and in
cache the element rate halves: saxpy avx2 f64/f32 = **0.50** in L1. In DRAM
the bytes per element double, so at equal GB/s the element rate halves again:
measured **0.47**. Both regimes give about 0.5x, but for different reasons
(lanes vs bytes). The scalar build is the exception in cache. Scalar fp32 and
fp64 run at the same element rate (5.30 vs 5.22 GFLOP/s in L1), because one
scalar op is one element in either width.

## 4. Alignment and vector tails (H5)

Figures: `plots/align_f32.png`, `plots/align_f64.png`, `plots/tail.png`.

**Alignment costs far more than predicted for wide vectors.** All arrays were
shifted by the same byte offset from a 64-byte boundary.

| f32, time / aligned time | offset 4 | 8 | 16 | 32 |
|---|---|---|---|---|
| mul avx512, L1 (N=2048) | 1.93 | 1.93 | 1.93 | 1.93 |
| mul avx2, L1 | 1.49 | 1.49 | 1.49 | **1.00** |
| saxpy avx512, L2 (N=65536) | 1.51 | 1.50 | 1.52 | 1.54 |
| saxpy avx2, L2 | 1.31 | 1.32 | 1.31 | **1.03** |
| any build, DRAM (N=4M) | 0.94-1.09 | | | |

The pattern is the cache-line split. A 64-byte zmm access at any non-zero
offset straddles two lines on *every* access, so avx512 is slow at every
offset. A 32-byte ymm access at a 32-byte offset never straddles a line,
which is why avx2 recovers fully at offset 32. In DRAM the split is hidden
behind memory latency (within +-9%, the run-to-run noise range there). The
prediction of 10-30% was right for sse2 (1.13-1.20x in L2) but not for wider
vectors, where every access splits.

**Tails behave as predicted.** For saxpy f32 at N=1 every build costs
~9-11 cycles per call, which is pure call/loop overhead. Cycles per element
then drop in a sawtooth at multiples of the vector width:
- avx2: 1.00 cycles/element at N=15, then 0.62 at N=16;
- avx512: 0.69 at N=31, then 0.32 at N=32.

The remainder runs as a slower epilogue. GCC adds a half-width epilogue loop
(16-byte for avx2, 32-byte for avx512; see `build/vecinfo/`), which smooths
the steps. By N=128 the costs have
converged to their steady state (avx512 0.14, avx2 0.21, scalar 1.52
cycles/element). The avx512 cost at N=17 is 4.3x its N=128 value, so tail
overhead matters up to about N=100, as predicted.

## 5. Stride (H6)

Figure: `plots/stride.png`.

**The SIMD gain disappears at stride 2.** With N=1024 (in cache at every
stride), avx512 saxpy f32 is 11.1x scalar at stride 1 and 1.07x at stride 2.
Every stride >= 2 sits at 0.90-1.07x for every build and both dtypes. In
cache this is not a memory effect. For stride > 1, GCC's
runtime stride check selects its scalar fallback loop (Section 1), so every
build runs the same scalar code.

**Useful bandwidth in DRAM (N=2M) falls with stride, and does not flatten.**

| stride (f32) | 1 | 2 | 4 | 8 | 16 | 32 |
|---|---|---|---|---|---|---|
| avx2 useful GB/s | 23.2 | 9.8 | 5.0 | 2.2 | 1.2 | 0.69 |

Up to stride 16 (one element per 64-byte line), the drop is 19x for a 16x
reduction in useful bytes per line. This matches the "1/stride" prediction,
plus a little extra cost per line. The predicted plateau past stride 16 did
not appear: stride 32 is another 1.7x slower. Two plausible causes, which we
did not test separately:
- the L2 adjacent-line prefetcher fetches lines in 128-byte pairs, so at
  stride 32 half the fetched lines are wasted;
- at stride 32 each 4 KB page holds only 32 useful elements, so TLB misses
  grow.

## 6. Roofline (H9)

Figure: `plots/roofline.png` (fp32). The ceilings are **measured** by
`src/peak.c` (`data/raw/peaks.csv`), one core:

| ceiling | value | per cycle |
|---|---|---|
| scalar (mul + add, no FMA) | 7.3 GFLOP/s | 2.0 FLOP |
| sse2 (mulps + addps) | 29.3 GFLOP/s | 8.0 FLOP |
| avx2 FMA ymm | 116.8 GFLOP/s | 31.7 FLOP |
| avx512 FMA zmm | 114.2 GFLOP/s | 31.0 FLOP |
| L1 / L2 / L3 / DRAM read | 429 / 157 / 51 / 21 GB/s | 118 B (L1) |

Two of these differ from the pre-measurement estimates:
- **Scalar peak** is 2 FLOP/cycle, not 4. FP multiply and add share ports 0
  and 1, so at most 2 scalar FP ops issue per cycle.
- **avx512 peak equals avx2.** That confirms a single fused 512-bit FMA unit.

Where the kernels sit (fp32):

- **DRAM:** every SIMD point is on the DRAM roof once write-allocate traffic
  is counted.
  - saxpy: 3.4 GFLOP/s = 20.4 GB/s useful.
  - mul: 1.29 GFLOP/s = 15.5 GB/s useful. Counting the read-for-ownership of
    `z` (16 B/element), that is 20.6 GB/s.
  - stencil: 8.3 GFLOP/s, i.e. 20 GB/s with write-allocate.
  - dot_simd: 5.4 GFLOP/s = 21.6 GB/s, read only.
  
  All sit at about 21 GB/s: memory-bound, as H9 predicted. The DRAM ridge
  point is 117 / 21, about 5.6 FLOP/byte, far right of every kernel
  (AI 0.08-0.63).
- **L1:** the L1 ridge is only 117 / 429, about 0.27 FLOP/byte.
  - saxpy (AI 0.17), mul (0.08) and dot (0.25) are left of it. avx512 saxpy
    reaches 57 GFLOP/s = 342 GB/s, **80% of the L1 read roof**.
  - The stencil (AI 0.63) is right of the L1 ridge, i.e. compute-side even in
    L1. It reaches only 52 GFLOP/s (45% of peak), consistent with being
    limited by its three overlapping unaligned loads per output rather than
    by FMA.
- **Scalar points** sit near the scalar *compute* ceiling, not on a
  bandwidth roof: scalar stencil 7.3 GFLOP/s = 100% of the 7.3 scalar peak,
  scalar saxpy 72%. In cache, the scalar build is compute-bound. That is
  exactly the headroom SIMD exploits.
- **Plain dot** sits far below every roof (1.9 GFLOP/s), on a ceiling the
  roofline does not draw: FP-add latency (Section 7).

## 7. Negative case: the dot product (H8)

Figure: `plots/dot_negative.png`.

**Plain dot: no speedup in any build, in any regime** (0.97-1.08x). The
measured cost is **4.03-4.06 cycles per element in sse2, avx2 and scalar**
(N=4096); avx512 is slightly slower at 4.46. Four cycles is the latency of
one FP add. Every iteration's add depends on the previous one: `s += x*y`
must keep strict left-to-right order without `-ffast-math`, because FP
addition is not associative.

Our hypothesis said this loop "will not vectorize". That was **wrong in
mechanism**. GCC 16 reports it vectorized: it does the loads and multiplies
in packed form (`vmulps ymm`), then adds the 8 products into the sum one at a
time (a chain of `vaddss`: a "fold-left" or in-order reduction). Strict FP
order is preserved. The result is bit-identical across all four builds (95.5
eps error for fp32 at N=1M in every build). Because the adds remain one
dependent chain, the packed multiply buys nothing. The performance prediction
holds even though the "does not vectorize" premise does not.

**omp simd dot: large gains, and they survive into DRAM.**
`#pragma omp simd reduction(+:s)` lets the compiler reassociate into vector
partial sums:

| omp simd dot, speedup vs scalar | L1 | L2 | L3 | DRAM |
|---|---|---|---|---|
| sse2 | 4.38 | 4.01 | 3.99 | 2.84 |
| avx2 | 9.08 | 8.06 | 6.99 | 2.94 |
| avx512 | 18.09 | 15.84 | 6.91 | 3.00 |

We predicted only a small gain in DRAM. That was wrong because the
*baseline* is not memory-bound. Scalar dot runs at 4 cycles/element, about
7 GB/s, a third of DRAM bandwidth. The SIMD version reaches the 21 GB/s DRAM
roof (Section 6), so 3x remains even out of cache. Even the SIMD version is
latency-bound in cache: avx512 runs at 0.229 cycles/element, i.e. 3.7 cycles
per 16-element vector. That is one FMA latency per iteration, so GCC kept a
single vector accumulator. Several independent accumulators, or `-ffast-math`
unrolling, could approach the L1 load limit instead. We did not test this.

**Second negative case: strided access** (Section 5). The compiler reports
the loop vectorized, yet at stride > 1 it runs at scalar speed. The
vectorized copy is guarded by a stride == 1 check, so the code that executes
is scalar. This is a loop that "appears SIMD-friendly", and that even the
compiler report calls vectorized, but it is not vectorized where it matters.
Only the disassembly shows it.

## 8. Anomalies and threats to validity

- **Frequency.** Laptop turbo varies. The median measured clock was 3.68 GHz;
  142 of 4440 size-sweep rows (3.2%) began below 3.3 GHz (minimum 2.81). The
  build loop is innermost, so a slow period hits all four builds of one
  point together, and speedups are computed within each repetition.
- **Cycles are estimated,** not counted: time multiplied by a frequency
  measured with a scalar dependent-add loop before and after each run. Any
  AVX-512 frequency licence during the timed loop is not captured. There is
  little sign of one: avx512 is more than 5% slower than avx2 at only 8 of
  185 fp32 size points. The exception is the plain dot product (4.46 vs 4.06
  cycles/element), where a small zmm frequency or latency penalty cannot be
  excluded.
- **Variance.** Median run-to-run CV of time is 2.5%. 177 of 1480 size
  points exceed 10%, and they are concentrated in DRAM (68) and at cache
  transitions (48), where sensitivity to background activity is expected.
- **Unexplained:** in L1, aligned saxpy f32 is *slower* than at a 32-byte
  offset for avx2 (0.65x) and sse2 (0.78x). Scalar mul at offset 32 is 1.30x
  slower. All arrays are shifted together, so their relative alignment is
  unchanged. A possible cause is 4 KB aliasing between the separately
  allocated arrays, but we did not verify it. One DRAM outlier: mul avx2 at
  8-byte offset, 1.29x.
- **Useful-byte accounting** excludes write-allocate traffic. This understates
  the true traffic of kernels that store (Section 6 corrects for it in the
  DRAM discussion).
- **One machine, one compiler** (gcc 16.2, Windows/UCRT). The single-channel
  DRAM and the single 512-bit FMA unit are specific to this laptop.
